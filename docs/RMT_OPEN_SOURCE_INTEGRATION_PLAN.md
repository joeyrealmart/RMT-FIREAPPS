# RMT Open-Source Integration Plan

## Current implementation

RMT FIREAPPS is a vanilla browser application in `outputs/fire-inspection-mvp/`:

- `index.html`, `styles.css` and `app.js` provide the Admin and Technician UI.
- `work/serve-fire-inspection-mvp.mjs` is a local Node HTTP server, bound to the LAN for physical-device testing.
- Authoritative online multi-technician records are file-backed shared job stores under `outputs/rmt-fire-local-data/shared-records/jobs/` and use server-side revisions and ownership checks.
- Schedules, device masters, inspection-run exports, request evidence, reports and other local prototype data are stored in the local data directory.
- Browser `localStorage` currently holds UI restore state, cached setup data and local drafts. It is not the intended authoritative multi-technician source.
- Photo Timestamp Evidence currently retains photo evidence through the established application/server flow. It must not be replaced during platform hardening.
- Reports are generated by the existing RMT report renderer; no third-party report engine is currently part of production.

The production application has no build pipeline, registered service worker or integrated IndexedDB implementation. A root `package.json` and lockfile now exist only for the isolated, pinned prototype tooling described below; production pages do not import those tools.

## Proposed components

| Component | Fit | Decision | Migration risk |
| --- | --- | --- | --- |
| Prompt Master | Development-only prompt checker/wrapper | NOW | None: no production runtime use |
| Dexie / IndexedDB | Persistent local drafts and mutation queue beneath existing server APIs | NEXT, feature-flagged adapter | Medium: must preserve localStorage drafts and server revisions |
| Workbox | Offline app shell and approved static mimic asset cache | NEXT after Dexie proof | Medium: stale cache/privacy mistakes can confuse field work |
| Sharp | Server-side derived photo generation while preserving originals | NEXT, isolated prototype | Medium: binary dependency and metadata integrity require QA |
| pdfme | Separate report proof of concept only | LATER evaluation | Low while isolated; production migration is not approved |
| QR package | Library evaluation and schema design | LATER | Low; must not alter extinguisher workflow yet |
| Supabase | Future architecture and migration design | LATER | High: no V1 migration or cloud dependency now |
| Appwrite | Alternative only | NOT NEEDED now | Avoid operating two backend stacks |

## Compatibility rules

1. Existing server shared records remain authoritative online.
2. Current `localStorage` remains available as a legacy cache/draft path until an explicit, verified migration is approved.
3. A queued local mutation must carry its operation ID, record revision and technician identity. Reconnect must call existing revision-protected APIs; conflicts must be surfaced, never overwritten.
4. Service-worker caching must be restricted to static shell assets and approved public mimic backgrounds. It must not cache mutation responses, authentication/session responses, private evidence or changing report data.
5. Photo originals remain immutable. Sharp may create a derived/stamped derivative only with linked metadata.
6. New tools must be isolated from the Wetex fixture, existing pin coordinates and current Photo Timestamp Evidence WIP.

## Safe implementation order

1. Development prompt tooling and this audit.
2. Add a standalone npm tooling manifest without changing the running app path.
3. Prototype a feature-flagged Dexie adapter with a test-only database name and focused persistence/idempotency QA.
4. Add an offline shell proof only after the Dexie adapter passes and cache boundaries are reviewed.
5. Prototype Sharp derivatives and pdfme outside the production report path.
6. Document QR and Supabase decisions before any production migration.

## Stop conditions

Stop and request approval if a change would alter frozen Wetex scopes, inspection history, pin coordinates, current report compatibility, Photo Timestamp Evidence records, or require destructive migration, credentials, payment or a paid service.
